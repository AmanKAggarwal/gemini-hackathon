Homeweave

Upload photos and floor plans of homes you like, plus a phone video of your current home. Homeweave builds one composite dream home, moves your real furniture into it, and lets you walk through the result.

The idea in one minute

  • Choosing. No single listing has everything. You like one home's kitchen and another's living room, and cannot see if they fit together.
  • Moving in. You cannot picture your own sofa and bed in a new space until moving day.
  • The new step, Correspondence. Each furniture group in your current home is mapped to the most similar spot in the new one. It is adapted from the paper Analogical Trajectory Transfer (arXiv 2605.14393), which moves paths between rooms. Homeweave moves rigid furniture instead.
  • The split. Gemini 4 sees, hears and judges. A geometric engine does the placing. A Gemini-only placement baseline shows where Gemini's spatial reasoning stops.

0. Project context

BuildPaste first in every coding session
You are my coding partner at a one-day hackathon. We are building Homeweave.

What it does: a user uploads listing photos and floor plans of homes they like, plus a phone video of their current home. The app builds one composite floor plan, moves the user's real furniture into it, and shows a 3D walkthrough.

Stack: Python 3.11, FastAPI, google-genai SDK, shapely and numpy for geometry. Front end is one HTML page with vanilla JS and Three.js. No database; JSON files in ./data.

Stages, each a pure function that takes JSON and returns JSON:
perceive_listing, perceive_home_video, judge_features, weave, generate_scene, arrange, judge_layouts.

Conventions, never break these:
- Units are metres. Right-handed axes, y up, floor at y = 0. Angles are degrees clockwise from +z seen from above.
- Ids are prefixed: src- for the current home, new- for the generated home, lst1-, lst2- for listings.
- Every object has a provenance field naming the photo, video timestamp or plan it came from.
- Unknown values are null with a reason string. Never guess a default.
- Every model response is validated against a pydantic schema. On failure retry once, then flag it.

Entities: Home {id, source, rooms[], fixtures[], scale_check}; Room {id, type, polygon, ceiling_height_m, doors[], windows[]}; FurnitureItem {id, category, dims_m {w,d,h}, pose {x,z,rot_deg}, front_dir, group_id, must_keep, confidence}; Layout {id, rank, placements[], costs{}, warnings[], leftovers[]}.

Models: gemini-4-hydrogen for perception, gemini-4-neon for hard plans and code, gemini-decision-1 (Decisions API) for judging. Placement is done by our own geometry code, not by a model.

How to work with me: give one file at a time, complete and runnable, with a tiny sample input and the command to run it. No placeholders. Ask before adding a dependency. Start by writing schemas.py with the pydantic models above.

1. Read one listing

RuntimeHydrogen · input: all photos and the floor plan of one listing
You are reading a real estate listing. You get its photos and, if present, its floor plan.

Return one JSON object matching the Home schema. No prose.

For each room: id (lst1-kitchen style), type, polygon in metres as [x,z] corners in order, ceiling_height_m, doors [{id, wall_index, offset_m, width_m, swing}], windows [{id, wall_index, offset_m, width_m}], fixtures [{id, type, footprint polygon}] for built-ins such as counters, islands, fireplaces, closets.

Also return staging[]: furniture visible in the photos, each with category, approximate dims_m, pose and the room it is in. These are placeholders, not the user's furniture.

Also return features[]: up to 8 things a buyer would like about this home, each {id, room_id, label, evidence: photo index}.

Scale rules:
- If the plan prints dimensions, use them and set scale_check.method = "plan_labels".
- Otherwise assume an interior door is 0.81 m wide, set scale_check.method = "door_width", and say which door you used.
- If a photo and the plan disagree on a room's size by more than 10 percent, keep the plan value and add the room id to scale_check.conflicts.

If you cannot see something, use null and give a reason. Do not invent rooms that appear in neither the photos nor the plan. Every room and fixture needs provenance naming the photo index or "plan".

2. Read the current-home video

RuntimeHydrogen · input: the phone walkthrough video
You are watching a handheld phone video of someone's home. Build an inventory of their furniture and the rooms it sits in.

Return one JSON object: {rooms[], items[], groups[], uncertain[]}. No prose.

rooms: as in the Home schema, ids like src-living. Estimate each polygon from what the camera shows.

items: every movable piece of furniture, each once, even if it appears at several moments. For each: id (src-sofa-01), category, dims_m {w,d,h}, pose {x,z,rot_deg} in its room, front_dir, against_wall (true or false), nearest_fixture (window, door, tv wall, fireplace or null), confidence 0 to 1, provenance {seen_at: [timestamps]}.

groups: furniture used together, each {id, kind, item_ids}. Kinds: conversation, sleep, dining, work, storage, other.

Scale: find a door in each room and assume it is 0.81 m wide and 2.03 m tall, then size everything else from it. Name that door in provenance. If no door is visible, set dims to null with reason "no scale reference".

Counting rules: if you are not sure two sightings are the same object, list it once and add a note to uncertain[]. Put any item with confidence under 0.6 in uncertain[] with a one-line question for the user, for example "Is the grey chair at 0:42 the same one seen at 1:15?". Ignore decor smaller than 0.3 m, people and pets.

3. Hard floor plans

RuntimeNeon, high thinking · only for scanned, hand-drawn or mixed-unit plans
This floor plan is low quality: it may be a scan, a phone photo of a hand sketch, or use mixed units. Read it carefully.

Work in this order and show the result of each step in a "working" field:
1. List every dimension label you can read, with its unit as written.
2. Convert all of them to metres.
3. Check that the walls of each room close into a polygon. Where they do not, say which label you distrust and why.
4. Check total area against any stated area.

Then return rooms[] in the same schema as the listing reader, plus plan_confidence 0 to 1 and unreadable[] listing anything you could not read. Use null with a reason for those. Do not fill gaps with typical room sizes.

4. Judge with the Decisions API

Runtimegemini-decision-1 · questions to send; take the exact request fields from the Decisions API guide
FEATURES (shared input: the photos of one feature, plus the user's rubric text)
Ask each as its own question and write the whole question in the instructions, because the model does not see your question keys.

yes/no: "Does this room get direct natural light from at least one window?"
yes/no: "Is the kitchen open to the living area with no full wall between them?"
yes/no: "Is there counter seating for at least two people?"
score 1 to 5: "How well does this space match the buyer's stated preference: {rubric line}? 1 = not at all, 5 = exactly."
score 1 to 5: "How much usable floor space does this room have for furniture? 1 = cramped, 5 = generous."

LAYOUTS (shared input: one top-down render and three eye-level renders of one layout)
yes/no: "Does every seat in the conversation group face another seat or the TV?"
yes/no: "Is there a clear walking path from every door to the centre of the room?"
yes/no: "Does any furniture block a window?"
yes/no: "Does the bed have clear floor on at least one long side?"
score 1 to 5: "How balanced is the furniture across the room? 1 = all on one side, 5 = evenly spread."
score 1 to 5: "Would this room feel comfortable to live in? 1 = awkward, 5 = natural."

Use: sum the scores in code, never ask the model to add. Rank the 5 layouts by total. If the top two are within 5 percent, show both to the user. Add a separate yes/no scope check ("Is this image a furnished room render?") instead of a "none of these" option.

5. Weave one floor plan

RuntimeNeon · input: the Home JSON for each listing and the scored features
You are merging the best parts of several homes into one floor plan a person could plausibly build.

Input: Home JSON for each listing, a ranked list of features with scores, and constraints {max_area_m2, bedrooms, bathrooms}.

Take the top-ranked room of each type. Arrange them on one level so that:
- every room is reachable through a door or opening, with no room entered only through a bedroom or bathroom;
- rooms do not overlap and shared walls line up;
- kitchen is next to dining or living; each bedroom is within one room of a bathroom;
- room sizes stay within 10 percent of their source listing;
- total area is under max_area_m2.

Return a Home JSON with source = "generated", ids prefixed new-, and for each room a provenance field naming the listing and room it came from. Carry over each room's fixtures and its staging furniture, moved with the room.

Also return conflicts[]: any feature you could not include and the reason in numbers, for example "lst2 kitchen island needs 4.2 m of width; the slot is 3.6 m". List a conflict; never squeeze or stretch a room to hide it.

6. The arrange engine

BuildThe core of the project. Paste after prompt 0
Write arrange.py and check.py using shapely and numpy.

check.py: check_layout(room, placements) returns {overlaps, door_blocks, clearance_fails, outside_room, relations_kept, violations_total}. It must work on any layout from any source, because we use it to score both our engine and a model baseline.
- Footprints are rectangles from dims_m and pose.
- overlaps: pairs of item footprints that intersect.
- door_blocks: items intersecting a door's swing, a quarter circle with radius equal to the door width.
- clearance_fails: rasterise the room at 0.1 m, inflate obstacles by 0.45 m, run A* from each door to every other door and to the room centroid. Each unreachable target is one fail.
- outside_room: items not fully inside the room polygon.
- relations_kept: share of same-group item pairs whose distance changed by less than 0.3 m and whose relative facing held within 30 degrees, compared with the source room.

arrange.py: arrange(src_room, src_items, groups, new_room, staging=None) returns up to 5 Layouts plus leftovers.
1. Describe each group in the source room: bounding box, whether it sits against a wall, the type of the nearest fixture, and which way it faces relative to that wall.
2. Candidates per group: for every wall of the new room long enough for the group's bounding box, slide the group along the wall in 0.25 m steps, with rotation in 90 degree steps and an optional mirror. The group moves as one rigid body. Items never scale.
3. Score each candidate: fixture mismatch (source group faced a window, candidate does not) weight 1.0; wall mismatch 0.5; clearance to doors and windows 1.0; distance from the matching staging group, if staging is given, 0.1. Keep the best 5 per group.
4. Assemble with beam search, width 5, largest group first. Add overlap between groups (weight 1.0) and change in distance between group centroids relative to the source room, scaled by the ratio of room sizes.
5. Refine each assembled layout: try moves of 0.1 m and snaps to the wall direction, keep any that lower the cost.
6. Run check_layout. Any item still breaking a hard constraint is removed and added to leftovers with a reason and the numbers, for example "needs 3.40 m; longest free wall is 3.10 m".
7. Return the 5 lowest-cost distinct layouts with their cost breakdown.

All weights live in one dict at the top of the file. Include a sample living room pair in samples/ and a __main__ that prints the check result for each layout. Target: under 2 seconds per room pair.

7. Gemini-only placement baseline

RuntimeNeon · the "where it breaks" comparison, scored by the same checker
You are arranging furniture. You get a top-down image of the person's current room, a top-down image of an empty new room, the new room's JSON (polygon, doors, windows, fixtures, in metres), and the list of furniture with dimensions.

Place every item in the new room so the arrangement feels like the old room, adapted. Keep items that were used together close together and facing the same way relative to each other.

Rules: no two items may overlap; nothing may block a door or its swing; leave walkways at least 0.9 m wide; every item must be fully inside the room. If an item cannot fit, leave it out and list it under leftovers with the reason.

Return JSON only: {placements: [{item_id, pose: {x, z, rot_deg}}], leftovers: [{item_id, reason}]}. Coordinates are metres in the new room's frame, angles in degrees clockwise from +z seen from above.

8. The 3D viewer

BuildNeon writes this well in AI Studio Build
Write viewer.html, one file, vanilla JS with Three.js from a CDN.

It loads home.json (a Home with rooms as [x,z] polygons in metres, doors, windows, fixtures) and layouts.json (up to 5 Layouts, each with placements {item_id, category, dims_m, pose}).

Scene: extrude each room polygon into walls 2.6 m tall and 0.1 m thick, with gaps at doors and glass panes at windows. Floor per room. Fixtures as grey boxes. Furniture as boxes sized from dims_m, coloured by group, with a small darker strip on the front face so facing is visible, and a text label above each.

Controls: a top-down orthographic view and a first-person view at eye height 1.6 m with WASD and mouse look, toggled by one button. Buttons 1 to 5 switch layouts and animate items to their new poses over 400 ms. A side panel lists leftovers with their reasons and the checker numbers for the current layout (overlaps, door blocks, clearance fails, relations kept). Items flagged by the checker get a red outline.

Add a "Render for judge" button that saves one top-down and three eye-level PNGs of the current layout to canvas data URLs and posts them to /judge. Use y up and angles clockwise from +z seen from above, matching the JSON.

9. Evaluation and stress ladder

BuildProduces the numbers for the submission form
Write eval.py.

Input: a folder of cases. Each case is one source room and one new room, as JSON produced by our perception stage from media filmed by people outside the team. The script must not contain any expected answers.

For each case run three methods: our arrange engine (top-1), our engine with the judge's pick from the top 5, and the Gemini-only baseline (call gemini-4-neon with the baseline prompt and the two top-down renders). Score every result with check_layout.

Report per method: share of layouts with zero violations, mean violations per layout, placement rate (items placed over items owned), relations kept, and runtime. Give each with a 95 percent bootstrap confidence interval over cases, and a paired bootstrap for engine minus baseline. Write results.csv and a results.md table. Log every baseline response that fails JSON validation as a failure, not a skip.

Stress mode (--stress): take each case and raise one dimension at a time until zero-violation rate falls below 50 percent, then record that level as the breaking point:
- furniture count: duplicate items to 15, 30, 60;
- scale gap: shrink the new room to 0.8, 0.6, 0.4 of its area;
- mirror: flip the new room;
- noise: jitter every item dimension by 5, 10, 20 percent.
Write breaking_points.md with one row per dimension and method: level where it broke, what failed first.

What the submission form will ask

Fill these with measured numbers from prompt 9. Do not write them before the run.

  • Hardest input. Longest and messiest home video that still gave a usable inventory, and the furniture count and scale gap where the engine stopped producing clean layouts.
  • What raw media gives that text loses. Room and furniture dimensions, how groups sit relative to windows and doors, and which way things face. Show one item's provenance: the video timestamp and the door used for scale.
  • Where it broke and what changed. The breaking points table, one fix you made after seeing a failure, and the new breaking point. Include the Gemini-only baseline result whichever way it comes out.
